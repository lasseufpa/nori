User guide
==========

Environment
-----------

NORI needs ns-3, the nr module, the OSC ``e2sim`` library compiled with the E2AP and
E2SM ASN.1 files of ``asn/`` and a patched ``asn1c``. The ``Dockerfile`` builds all of
them on Ubuntu 24.04 (GCC 13, CMake 3.28, Python 3.12).

.. code-block:: bash

   # image nori-nori-dev:ns3.48-nr5.1, container nori-dev
   docker compose up -d
   docker compose exec nori-dev bash

The compose file mounts the repository at ``/home/developer/ns-3-dev/contrib/nori``
and uses the host network, so the SCTP association to the RIC leaves from the host
address. The image accepts the build arguments ``NS3_VERSION`` and ``NR_VERSION``.

Building
--------

Inside the container:

.. code-block:: bash

   cd /home/developer/ns-3-dev
   ./ns3 configure --enable-examples
   ./ns3 build nori-testbed-scenario     # or ./ns3 build for everything

Optimized build
^^^^^^^^^^^^^^^

The ``default`` profile keeps assertions and logging. The ``optimized`` profile
(``-O3``, native CPU optimizations, no assertions) ran the testbed scenario about
2.3 times faster in the measurements of :doc:`validation`. Keep ``--enable-logs``
to see the ``NS_LOG`` messages of NORI:

.. code-block:: bash

   ./ns3 configure --build-profile=optimized --enable-examples --enable-logs \
         --enable-modules=nori
   ./ns3 build nori-testbed-scenario

To keep both builds, configure the optimized one in a copy of ``ns-3-dev`` that links
``contrib/nori`` to the original directory. ``./ns3`` keeps one configuration per
source tree.

Connecting to a Near-RT RIC
---------------------------

Requirements on the RIC side:

* the E2 Termination SCTP port must be reachable from the simulation host. In a
  Kubernetes deployment of the OSC RIC this is usually a NodePort (for example
  ``32222``) on the node address;
* the xApps must subscribe to the E2 node names announced by NORI
  (``gnb_268_341_<cellId as 8 digits>``, see :doc:`architecture`).

Scenario side:

.. code-block:: c++

   // realtime clock: required with a real RIC
   GlobalValue::Bind("SimulatorImplementationType",
                     StringValue("ns3::RealtimeSimulatorImpl"));

   Config::SetDefault("ns3::E2Interface::E2Periodicity", DoubleValue(1.0));

   Ptr<E2TermHelper> e2Helper = CreateObject<E2TermHelper>();
   e2Helper->SetAttribute("E2TermIp", StringValue("10.10.20.142"));
   e2Helper->SetAttribute("E2Port", UintegerValue(32222));
   e2Helper->InstallE2Term(gNbDevs);   // one E2 node per gNB

The helper must stay alive for the whole simulation (keep the ``Ptr`` in ``main``).

Run with the logs of the E2 path:

.. code-block:: bash

   NS_LOG="E2Interface=level_info|prefix_time:CccControlMessage=level_info|prefix_time" \
   ./ns3 run "nori-testbed-scenario --simTime=0 --enableE2=true --enableRealtime=true \
     --ipE2TermRic=10.10.20.142 --ipE2TermRicPort=32222 --trafficScale=5"

Expected sequence in the output:

.. code-block:: text

   [e2sim-mod.h] Connecting to RIC at 10.10.20.142:32222 ...
   [e2sim-mod.h] SCTP Connection established (fd=3)
   [e2sim-mod.h] Received SETUP-RESPONSE-SUCCESS from Near-RT RIC
   KPM subscription requestorId ...: reportingPeriod 1000 ms, granulPeriod 1000 ms
   Starting KPM reports for requestorId ...
   CCC RIC Control received.
   Applying CCC control from RIC (requestorId=1, 3 quotas)

Troubleshooting
---------------

.. list-table::
   :header-rows: 1
   :widths: 40 60

   * - Symptom
     - Check
   * - No ``SCTP Connection established``
     - RIC address and port; the E2 Termination service must expose SCTP. The local
       port ``E2LocalPort + cellId`` must be free (an old simulation may still hold
       it).
   * - E2 Setup succeeds but no ``KPM subscription`` line
     - The KPM xApp did not subscribe: check its logs and the E2 node name it uses.
   * - Controls received but throughput does not change
     - The cell is not loaded, or the max ratio is high (see :doc:`scheduler`).
   * - The xApp does not receive RIC Control Acknowledge
     - Route of message type 12041 in the RIC routing manager (see :doc:`e2ap`).
   * - Controls arrive farther apart in simulated time than expected, or closer
     - The simulation is slower than real time; see :doc:`architecture`.
   * - ``... queued but the drain event is not started``
     - The scenario installed the E2 objects without ``E2TermHelper``; schedule
       ``E2Interface::StartSctpQueueDrain`` from the simulation thread.

Building this documentation
---------------------------

.. code-block:: bash

   python3 -m pip install -r doc/requirements.txt
   make -C doc html          # Sphinx manual -> doc/build/html
   make -C doc doxygen       # API reference -> doc/build/doxygen/html

The attribute tables of :doc:`attributes` are generated by the
``nori-print-attributes`` program (see that chapter).
